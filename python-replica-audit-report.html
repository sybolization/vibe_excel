🧠 理解检查

6 道情景题。选完后提交，系统给分并展开全部解析。

1. 你接手了一个仓库，`vibectl plugins` 显示 sessions 为 PENDING，其余为 ACTIVE。最合理的下一步？

正确答案 A：PENDING 表示依赖服务未就绪，插件根本没有 apply。宿主按服务可用性激活插件，先查 inject 缺口才是根因。
B 与 D 都是绕过依赖链：sessions 需要 store/workspace/exec/agent/telemetry/commands 六个服务，删配置只会失去编排能力。
C 是误判：PENDING 不是时序抖动，重启不会让缺失的服务凭空出现。

2. 一次 run 双跑一致，你随后又提交了一次草稿，然后执行 publish。系统会怎样？

正确答案 C：发布前必须比对 run.json 的 codeCommit 与当前草稿 HEAD。否则会把从未双跑过的提交合进 main，而证据仍写着上一次运行。
A、B 都忽略“证据属于哪一版代码”这个前提；双跑只证明过去那个 commit 是确定的。
D 看似稳妥，但 publish 不是执行阶段：它只发布已有证据，不会替你做验证。

3. 为什么双跑比对只比“声明的产出”（outputs 表 + out 目录文件），而不是整库哈希？

正确答案 B：双跑的目标是证明“同一输入 + 同一代码 = 同一产出”。库内的时间戳等元数据天然不确定，必须用声明产出作为比对范围。
A 是性能理由，却不是设计理由；即便很快，非确定内容仍会让比对红色。
C、D 与事实不符：比对在本地进行，且所有表都在 SQLite 中。

4. 你在补丁里写了 config: {keep: 9}，想给某插件“只改一个键”。系统为什么整体替换 config？

正确答案 D：补丁按 id 覆盖，写出的字段就是最终值；深合并会让旧键悄悄残留，排查“我明明改了却没生效”会变得困难。
A 不正确：YAML 本身与深合并策略无关，是宿主选择了整体替换。
B、C 是想象出来的副作用；核心是配置可解释性，不是资源或加载次数。

5. 中文化时，某条错误消息里出现 hr.db 与 run.json。正确处理是？

正确答案 A：文件名/路径是跨模块契约，book、encoder、session 都按名字读取；说明文字才是用户界面文案。
B、D 会改变磁盘契约，导致读取方找不到文件；D 还扩散了改动面。
C 过度保守：注释、docstring、错误说明都可以翻译，保留的是标识符而不是整句。

6. 数据库快照为什么用 VACUUM INTO，而不是直接复制 hr.db 文件？

正确答案 C：WAL 模式下已提交事务可能还在 -wal 文件里。VACUUM INTO 通过 SQLite 自身生成一致性副本，再配合内容寻址与完整性校验。
A 不是关键：一致性和正确性优先于速度。
B 只是附带效果；D 与 SQLite 快照语义无关。

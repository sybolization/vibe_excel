### 3.4 PN 看板那 18 行：17 行对上，1 行暴露的是**缺输入**

人工维护的 `PN余量` sheet 有 18 行，程序算出的 208 组里能覆盖 17 行，`剩余空号` 与 `本批已用` 全部对上。

剩下 1 行：`Hu, Shenglin / 8141-1614 / Direct Labor`，看板写 `剩余 0、本批已用 0`，
而这两份源表里这个三元组**一行都没有**。也就是说这一行不是从「可用岗位 + 本批已发」推出来的，
它来自一份没给我们的**主管/岗位主数据**。

这不是算错，是缺输入——而这正是「有标签」的价值：没有这 18 行，我们只会说「程序跑通了」。

## 5. 数据里真实存在的问题（模型报告 + 我的核对）

1. **`new_hire.PayRate` / `re_hire.PayRate` 已经有值，而且不是全 2800**：`new_hire` 是 2800 × 21,294 + 2600 × 4,325。
   用户说「其余均为 2800」，到底覆盖还是保留？**没有人回答过这个问题**。
2. **159 个「本批已发」岗位号与 6,337 个「可用岗位」零交集**——说明「可用岗位」表导出时已经把这批扣掉了。
   所以 `remaining` 是**已净额**，不能再减 `sent`。我第一版核对脚本就是在这里算错的（算成 `剩余 = 可用 − 已发`，18 行里 17 行对不上）；
   模型独立发现了同一件事并写进了待确认项。
3. **证件号脏**：9,997 个含 `*` 的掩码值；3,064 个重复值（762 个是掩码撞车、2,302 个是真实身份证重复，最多重复 8 次）。
   下一轮「以身份证号做 Vlookup」时必然遇到一对多。
4. **日期列混着序列号与文本**：`employees` 14 列是 Excel 序列号（325 行带时间小数）；
   `new_hire`/`re_hire` 反而是文本 `YYYY-MM-DD`。`毕业年` 列名是「年」，30,269 行存的是日期序列号。
5. **36 列整列为空**（`new_hire`）、33 列（`re_hire`）；`positions.effective date` 整列空。
6. **`#N/A` 是字符串不是空值**：`positions` 第 8 列 24,348 个 `'#N/A'`、17 个数字。

## 6. 模型自己提出的 7 个待确认项（原样保留）

1. 员工状态里用户没点名的取值：`实习 17` / `待离职 258` / `退休返聘 28`——字面口径保留、保守口径排除，当日差集 0 人。
2. 用工类型里用户没点名的取值：`临时工/兼职 1` / `实习生 122` / `派遣员工 52` / `退休返聘 54`——两口径都没排除，要不要排？
3. `员工级别` 有 179 行为空（不是 `Exempt`）：按「未标注」处理；实际影响 0 行。
4. 有 2 个分组只出现在 `sent_positions`：分组集合取并集（208）还是只取可用岗位（206）？
5. **`remaining` 是否已净额**（见 §5.2）——这是唯一影响 208 个分组口径的问题。
6. 入职日期 325 行带时间小数，同日判定按整数日比较。
7. 当日 146 行里有 1 行被筛掉：`瞿威 / HW Batching / 外包员工`。

> 这 7 条就是「用户确认流程」要承接的输入。目前它们只存在于一份 JSON 里，**没有人能点确认**。

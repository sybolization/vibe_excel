# ADR-0007：工作流是版本单位，节点是函数，边是表

- 状态：已采纳（§2 的 `nodes` 声明与 §7 的提示词契约已被 [ADR-0008](0008-code-as-flow.md) 修订；
  §3 的比对口径与 §4 的证据要求于 2026-11-05 收紧，见文末补记）
- 日期：2026-11-04
- 取代：`stage-molex` 的「阶段包」声明（import / analyze 两个 stage）

## 背景

此前编排器用「阶段」（stage）描述业务：一个阶段 = 一个入口文件 + 一段参数模板 + 声明的产出。
它的问题是**把一件连续的事切成了几个硬边界**：

1. 建表和写脚本本来就是同一个域。跑一次发现异常，你要么查表、要么查脚本——它们在同一次判断里，
   分成两个阶段只会让人以为「建表阶段结束了」。
2. 阶段由插件声明，模型改不了；而真正决定口径的是模型写的代码。声明和代码各说各话。
3. 「表」在体系里几乎没有位置：它既不是节点也不是边，只是一行 `mutatesDatabase: true`。

## 决策

### 1. 版本管理「流」，不管理零件

`flow.json` 是程序仓库里的一个文件，跟代码一起提交、一起发布。它的摘要 `flow@<12>` 就是这次运行的版本号。
数据不进版本：数据在运行时作为输入绑定。

### 2. 图的三种元素

```json
{
  "flow": "molex-prep",
  "db": "hr.db",
  "materialize": [
    { "file": "可用岗位表_2026-10-22.xlsx", "sheet": "可用岗位", "table": "available_positions",
      "columns": { "岗位号": "position_id", "归属主管": "supervisor", "地点": "site" } }
  ],
  "outputs": ["population", "pn_available"],
  "nodes": [
    { "id": "build_population", "call": "pipeline.py:build_population",
      "reads": ["employees", "available_positions"], "writes": ["population"] }
  ]
}
```

- **物化**：文件 → 表，只做「选 sheet、选列、改名」。**不允许有业务规则**——有规则的东西必须落在节点上。
  没被物化成表的文件，不能进计算图。
- **节点**：`file.py:function` 或 `file.sql`。入参由函数签名声明（`db` / `inputs` / `out` / `as_of` / `report`），
  平台按签名过滤传参。不传 ctx：ctx 会把依赖藏起来，而这一整套设计的目的就是把依赖摊开。
- **边**：一张 SQL 表。上游写的表就是下游能读的表，不另外画线；一张表只能有一个生产者。

### 3. 一次运行 = 两遍

`run` 默认跑两遍：两轮各自从同一份数据快照出发、各自写自己的库，比的是**声明的产出**
（`outputs` 里的表 + out 目录里的文件）。一致才把第一轮的结果提升到工作区并登记数据版本；
不一致就是这次运行失败。

全库逐表比对暂缓：库里还有 `meta.created_at` 这类非确定内容，全量比对会一直红。这条留待
「程序不写系统时间」成为可强制检查的规则之后再启用。

### 4. 发布只认证据

`publish` 不再接受「先手动跑一次 verify 再发布」。证据就在那次运行的 `run.json` 里
（`status: succeeded` 且 `identical: true`）；拿不到就拒绝合入。

### 5. 最短路径是人的决定

节点按用户描述写，优先业务准确性；不做自动折叠。折叠会改变口径（合并两张中间表，等于删掉一个
可以单独检查的中间结果），所以它是一个**两段式的命令**，不是一个自动步骤：

1. `optimize`：模型在**只读的干净 worktree** 里读代码和 flow，把建议写成一份 JSON
   （每条必须有 `risk` 和 `verify`——写不出验证办法的建议不接受）；
2. `optimize --apply=<id>`：只实现被批准的那一条，改完按批准的 `verify` 自证等价。

建议文件带 `flowDigest`：流程改过之后旧建议自动失效，防止「拿旧地图改新代码」。

### 6. 模型可以中途问人（`ask_user`）

口径类问题（「离职再入职算不算新人」）不让模型猜。程序通过 `packages/harness/ext/ask-user.ts`
给 pi 挂一个扩展，注册 `ask_user` 工具；在 RPC 模式下它变成一条 `extension_ui_request`，
宿主（`agent-pi` 插件）把它转给终端里的人，拿到回答再按同一 `id` 写回子进程的 stdin。
一问一答落进 `runs/<trace>/questions.jsonl`。

pi 的 `RpcClient` 没有暴露回话口，所以 `writeUiResponse()` 直接写子进程 stdin——
绕开的是客户端封装的缺口，协议本身是公开的。等不到回答（非交互环境 / 超时 / 用户取消）时
按 `cancelled` 回，模型收到的是「未确认」，**不是**「用户同意」。

### 7. 提示词是契约的一部分

`prompts/author-flow.md` 是模型唯一的说明书，和加载器接受的东西必须一致：
`test/prompt-contract.test.ts` 会检查占位符都有值、契约关键字都在（物化只做映射、节点是函数、
双跑、按描述写不折叠）。契约改了而提示词没改，这条测试会红。

## 后果

- 正面：流程只有一份声明，和代码同版本；表的依赖可校验（环、重复生产者、物化冲突、悬空读）；
  双跑不再是一个可选命令，而是运行的一半；发布有据可查。
- 负面：`stages` / `stage-molex` 两个插件被删除，旧程序仓库里的 `import_hr.py` / `analyze.py` 还没有迁移成
  `flow.json` + 函数节点；提示词已按新契约写好，真实模型也已跑过（见 [ADR-0008](0008-code-as-flow.md) 缺口 2）。
- 未做：全库双跑比对、写阶段跨表原子。

## 补记（2026-11-05）：§3 与 §4 各收紧一处

**§3「比声明的产出」有个漏洞**：两轮**同时缺同一张表**时，两边都缺，`diffRounds` 判成「一致」，
发布照过——那是空集合相等，不是结果相等。空 `outputs` 更彻底，双跑退化成「两轮都没崩」。
现在每轮收尾先核对声明的产出表是否真的出现：缺一张或 `outputs` 为空，都判该轮失败
（`flow-run.ts` 的第三步）。这是收紧，不是放宽：以前能过的「什么都没产出」现在过不了。

**§4「发布只认证据」补了一条**：证据里的 `codeCommit` 必须等于**草稿分支现在的 HEAD**。
`mergeInto` 合的是分支 HEAD，不是 run 记下的那个 commit，所以「run 通过 → 再 author 一次 → publish」
在修复前会把没双跑过的提交一起合进 main，而证据上还写着上一次的 run。现在对不上就拒绝，
并点出两个 8 位 commit。

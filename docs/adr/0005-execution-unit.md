# ADR-0005：执行单元——入口契约、输入批次与「每次都是干净执行」

- 状态：已接受（实现落在 `spikes/demo-real-data`，S2 的 `packages/harness` 会吸收）
- 日期：2026-10-30
- 相关：指南 §3.4、§6.1、§6.3、§6.4、§6.5、§12 S1/S3；ADR-0002（版本模型）、ADR-0003（重跑）、ADR-0004（发布）

## 1. 问题

模型写出程序之后，**系统怎么执行它**，才同时满足三件事：

1. 这次执行能精确对应到一个代码版本（否则恢复四元组是假的）；
2. 换一台机器、换一个目录、过一周再跑，结果一样（否则"干净重跑"只是仪式）；
3. 数据只读副本、不进 Git、不因为有人在原始目录上动文件而变化。

M0 之前只验证了「模型能写程序并自己跑通」。真实数据这一次暴露出：**"模型自己跑通"和"系统可复现地执行"是两件不同的事**。

## 2. 决策

### 决策 1：入口契约由编排器定义，程序不能假设 cwd

每个阶段有一个固定的调用方式，写进提示词、写进编排器，模型不能改：

```
<python> import_hr.py  --inputs <DIR> --db <PATH>
<python> analyze.py    --db <PATH> --out <DIR> --as-of <YYYY-MM-DD>
```

- 所有路径从参数进来，程序里不许有绝对路径、不许依赖当前目录；
- 参数缺失 → 打印用法 + exit 2（编排器据此区分"跑错"和"跑失败"）；
- 业务日期用 `--as-of` 显式传入，不读系统时间。

原因：只有这样才能把同一个程序放到 `worktree --detach` 出来的**任意目录**里执行。
本次两次 author 各让模型自查过「grep 不到硬编码路径」，实测有效。

### 决策 2：输入批次内容寻址，只读副本进会话工作区

```
work/inputs/<batchId>/manifest.json      # 每个文件的 sha256 + bytes
work/inputs/<batchId>/files/<原文件名>
batchId = sha256(按文件名排序的 [{name, sha256, bytes}]) 前 12 位
```

- 程序只读 `work/inputs/.../files`，**永远不读 `ground_true_excel` 原目录**；
- 同一批文件重复 `setup` 不会产生第二份副本（幂等）；
- `runs.input_batch_id` 存的就是这个 id，恢复时用它定位"当时用的是哪份输入"。

原因：原目录是用户的工作目录，随时会被覆盖或重命名。用内容寻址之后，"这次跑的到底是哪 5 个文件"不再依赖记忆。

### 决策 3：每次执行都是干净执行（run ≡ clean run）

`run` 不直接在会话 worktree 里跑，而是：

1. 取 `draftHead`（草稿分支当前提交）作为 `commit`；
2. `git worktree add --detach <runDir> <commit>` 开一个全新目录；
3. 在该目录里执行入口契约，环境是白名单（**不含 `OPENCODE_API_KEY`**）；
4. 执行完移除 worktree，把产物复制到 `runs/<id>/clean/...-artifacts/` 并写 `manifest.json`。

由此得到：

- `runs.code_commit` 是精确的——不需要"事后猜这次是哪个版本"；
- **"干净重跑"不再是一个额外流程，它就是执行本身**；`verify` 只剩一件事：同 commit 跑两次、比内容哈希。

代价：每次执行都要 checkout 一份程序（毫秒级），以及产物必须落到 worktree 之外（见决策 4）。

### 决策 4：数据版本记「输入」，产物记 `artifacts`

`beginRun` 记录的是本次执行**读的是哪一版数据**（`data_revision_id`），不是它产出了什么。
产出走 `artifacts`（`kind` / `path` / `sha256` / `bytes`）；如果一次执行改变了业务库，执行后再 `VACUUM INTO` 出一个**新**数据版本，作为下一次执行的输入。

本次实例：

| run | code | 输入数据版本 | 产出 |
|---|---|---|---|
| `import` | `e827393` | `838b0441`（空库基线，12,288 B） | `hr.db` 74 MB + 新版本 `6db79c22` |
| `analyze` | `17ad40cc` | `6db79c22`（上一轮产出） | 4 个文件（含 `summary.json`） |

原因：把「读了什么」和「写了什么」分开，才能回答"这个结果是用哪一版数据算的"，也才能支持"同一程序换数据重跑"。

### 决策 5：阶段化，而不是一个大脚本

用户流程有 59 行，一次让模型全部实现必然做成一个巨脚本。这里把它切成有名字的**阶段**（`import` / `analyze`），
每个阶段：独立提示词 → 独立提交 → 独立 run → 独立产物。

实际效果：第二轮 `analyze` 在模型侧只花了 335s（比第一轮 426s 短），因为它读的是已经录入好的库，不需要再碰 60 MB 的 xls。

### 决策 6：独立核对是发布证据的一部分，不由被测程序提供

发布前要求 `analyze` 的确定性证据（同 commit 跑两次、内容哈希一致），
此外用**第二实现**（`tools/verify_outputs.py`，从原始 Excel 重算，完全不读被测程序）核对行数、分类计数、分组结果。

本次的实测价值：这一份核对抓到了「`remaining` 到底是净额还是要再减 `sent`」——我第一版写错，模型和看板都对。

## 3. 验证（真实数据，2026-10-30）

- 录入 117,776 行、0 行 quarantine；模型自己跑出的库与提交后用干净 worktree 跑出的库，**7 张表内容哈希完全相同**；
- `import` / `analyze` 各连跑两次，内容哈希逐表一致（`verify.json` 里 `identical: true`）；
- 独立核对 23/23 项通过（明细见 [RESULTS.md](../../spikes/demo-real-data/RESULTS.md)）；
- 从快照恢复：删掉 employees 一半（60,248 → 30,124）后恢复回 60,248，内容哈希与删除前一致；
- 会话锁：持锁进程存在时另一个进程申请被拒（带 pid 与起始时间）；
- 发布：证据文件 → `merge --no-ff` → main `77750ae8`，发布记录写明证据路径。

## 4. 已知缺口

1. **author 阶段是灰区**：模型写程序时会自己跑一遍调试，这些执行**不在干净 worktree 里、也不计 `run`**。
   本次两个阶段都是这样迭代出来的。理想做法是记录"试跑"为低权重事件，现在完全没记（只留下事件流里的 bash 输出）。
2. **进度可见性不足**：author 一次 7 分钟，编排器的 `console.log` 被管道缓冲，前 6 分钟看不到任何输出
   （只能去看 `events.jsonl`）。长任务必须自己推进度，不能指望 stdout 及时刷出来。
3. **阶段间依赖是隐式的**：`analyze` 依赖 `import` 产出的库，靠"取最新数据版本"串起来；没有显式依赖图，
   也没有"上游版本不在就跑不起来"的检查。
4. **发布证据仍是调用方给的路径**：任何人可以伪造一个 `verify.json`。与 ADR-0004 缺口 1 同源，仍未解决。
5. **`getSessionStats()` 必须在 `client.stop()` 之前调用**：本次两个 author 的统计都是在 stop 之后取的，拿到空对象，
   只能事后从事件流的 `turn_end.message.usage` 里聚合（1,626,450 tokens / $0.056）。
6. **只验证了单机、单会话**：两个会话并发没有实测；锁不跨机器。
